# src/screens/ — route-level screens

Parent: [`../CLAUDE.md`](../CLAUDE.md) → [`/CLAUDE.md`](../../CLAUDE.md).
Any change in this folder updates this file and the root repo map/phase
table in the same change.

**Status: all four screens built, routing fully wired, Phase 6 motion
pass landed.** `App.jsx` mounts `<BrowserRouter>` with routes for all
four. `TitleScreen.jsx` and `EpisodeView.jsx` now use Framer Motion's
`useReducedMotion()` instead of an inline `window.matchMedia` check (see
the note below — this was patched in one sweep across both files, not
file-by-file, per the note that used to be here). `EpisodeView.jsx`
wraps its episode-title-card dismissal in `AnimatePresence` (spec 3.5
"Chapter open") and wraps each content panel in
[`../components/RevealPanel.jsx`](../components/CLAUDE.md) for the
scroll-reveal + parallax. `ChapterSelect.jsx` wraps its grid cards in the
same `RevealPanel.jsx`. `TitleScreen.jsx` deliberately does **not** use
`AnimatePresence` for its beat swaps — see the note in that file for why
(spec 4.1's own stage directions call for a hard cut, not a dissolve, and
a dissolve here would flash the page's `--paper` background between
beats since nothing is mounted behind the departing beat).

| `TitleScreen.jsx` | `/` | ✅ | Sequences `StartPrompt` → `PresentsCard` → `TitleReveal` → `MainMenu` (see [`../components/CLAUDE.md`](../components/CLAUDE.md) — all four now exist). Owns the beat-progression state and a window-level `keydown` listener (Tab/Shift excluded) so every beat is skippable by click, tap, *or* key, per spec §4.1. `StartPrompt` (beat 0, **new this batch**, not in spec §4.1's original list) is gated by the same session-scoped `hasPlayedIntro` flag as the rest — a genuine fresh visit opens on it, a same-session SPA return to `/` skips straight to `MainMenu` as before. Beat swaps are a plain conditional render, not `AnimatePresence` — see the doc comment at the top of this file for why a cross-fade here would contradict spec 4.1's own "cut to" stage direction. **Fixed this batch:** the 3-beat intro was replaying in full every time `/` was reached from inside the app (e.g. `ChapterSelect.jsx`'s "← Title" link, `PlainResume.jsx`'s "Back to the interactive version" link) — jarring on a SPA nav where the visitor just saw it seconds ago. A module-level `hasPlayedIntro` flag (deliberately not `useState`/context, since it must outlive this component's unmount on route change but still reset on an actual page reload) now makes the intro a once-per-browser-session thing: it flips true the first time the `MENU` beat is reached, and the component's initial `beat` state reads it, so any later mount of `/` in the same session opens straight on `MainMenu`. A genuine fresh load/refresh still gets the full `PresentsCard` → `TitleReveal` sequence. Fires `sounds.intro` (see `../lib/CLAUDE.md`) — a short synthesized signature motif, the user's "Netflix ta-dum" request — reusing the exact same `hasPlayedIntro` flag (checked before it flips) so it plays once per session and never replays on a same-session SPA return to `/`. Routes through `useSound()`, so it respects the Settings sound toggle and browser autoplay policy like every other cue in the app. **Retimed this batch:** it now starts the instant beat 2 (`TitleReveal`) is reached, not beat 3 — "play it the moment the second loading screen comes" — and is actively cut off (not just left to finish) the moment `beat` moves on to `MENU`, via a `stopIntro` closure returned from `playSound('intro')` and called from the triggering effect's cleanup function. That cleanup fires whether `TitleReveal`'s own hold times out naturally or the visitor skips it early, so the sting reliably ends exactly when the menu appears regardless of how that beat ended. Also documented here: a live "the sound doesn't play on reload" report turned out to be correct browser behavior, not a bug — beats 1–2 auto-advance with zero interaction required, so a visitor who never clicks/taps/presses a key during them never produces a user gesture on that pageload, and no cue (not just `intro`) can play without one. See the doc comment at the top of this file and `../lib/CLAUDE.md` for the full explanation. **Then a real bug turned up in that same area** ("I still can't hear shit until I CLICK"): the beat-2 effect used to call `playSound('intro')` and flip `hasPlayedIntro` unconditionally, even when reached via `TitleReveal`'s own timer with no gesture yet — the attempt correctly failed silently, but the one-shot flag was already spent, so a later click could never trigger it again. The effect now checks the new `hasHadUserGesture()` export from `../lib/sound.js` first; if a gesture already happened it plays immediately as before, otherwise it attaches a one-time `pointerdown`/`keydown` listener (only while beat 2 is showing, torn down on the same cleanup that stops the tune) and plays on the first real one instead. See `../lib/CLAUDE.md` for the full mechanism. **Root cause finally addressed this batch, not just chased:** a live report ("I can't hear any sound... UNTIL I click on the website which is poor") made clear that catching an *incidental* click was never going to feel reliable, because there usually wasn't one that early. `StartPrompt` (beat 0) now asks for that click explicitly, up front, before anything else in the sequence — so by the time beat 2's effect runs, `hasHadUserGesture()` should already read `true` every time, and the `pointerdown`/`keydown`-wait branch becomes a safety net rather than the primary path. Verified live end-to-end: `navigator.userActivation.hasBeenActive` reads `false` while `StartPrompt` shows, and a single keypress on it both flips that to `true` and — confirmed via a patched `createOscillator` — results in all 5 of `sounds.intro`'s voices actually firing once beat 2 is reached. |

## Rules for whoever builds these

- Every screen reads from `../data/episodes.js` — no hardcoded copy.
  (The site owner's name/tagline and UI chrome labels like menu items are
  treated as shell identity, not resume content, matching the existing
  precedent in `PresentsCard.jsx`.)
- Every screen must be keyboard-navigable start to finish; this is a
  requirement, not a nice-to-have (spec §2 rule 1). Verified manually via
  keyboard-only pass through all four screens.
- **Resolved (Phase 6):** `useReducedMotion()` (Framer Motion's hook) has
  replaced the old inline `window.matchMedia('(prefers-reduced-motion: reduce)')`
  check in both `TitleScreen.jsx` and `EpisodeView.jsx` (the only two
  files that had it), in one sweep, combined with `useSettings().motion`
  the same way as before — either one being "reduced" disables motion.
  `ChapterSelect.jsx` and `PlainResume.jsx` never had inline motion
  checks of their own; `ChapterSelect.jsx`'s new `RevealPanel.jsx` usage
  does its own combined check internally.
- Update this table's status column and the root `CLAUDE.md` Phase 4/5
  rows the moment any of these four files changes meaningfully.
