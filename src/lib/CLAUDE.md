# src/lib/ — non-visual utilities

Parent: [`../CLAUDE.md`](../CLAUDE.md) → [`/CLAUDE.md`](../../CLAUDE.md).
Any change in this folder updates this file and the root repo map in the
same change.

**New folder this batch.** Everything else under `src/` fit one of the
existing categories (`components/` = presentational + interaction
plumbing, `context/` = React state, `data/` = content, `screens/` =
routes, `styles/` = CSS, `assets/` = static files) — a sound *engine* is
none of those. It has no JSX, isn't a React Context, and doesn't own any
component-shaped state, so it lives here instead of being awkwardly
homed in `components/`.

**This batch — real fix for "still can't hear it without headphones,"
not another gain bump.** Every previous "louder" pass (there were three)
only ever raised a cue's own `gain` value, because every voice connected
straight to `audioCtx.destination`, which hard-clips past 1.0 — that
ceiling was the actual bug, and it's why the reports kept coming back
even after `intro`'s chord was already tuned to sum to ~0.95, right at
the edge of what destination could take. `sound.js` now has a
`getMasterInput()` master chain (compressor → fixed 3.2x makeup gain →
brickwall limiter → destination) that every voice in `blip()` routes
through instead of connecting to destination directly. The compressor
evens out simultaneous voices (e.g. `intro`'s chord) before the makeup
gain boosts the whole signal several times over, and the limiter
guarantees that boost can never actually clip — this is what buys real
headroom instead of just re-raising numbers that were already maxed out.
`navigate`/`select`/`toast` also got a smaller supporting gain bump
(0.04→0.1, 0.075→0.16, 0.05→0.12) now that there's a chain to safely
carry it. Verified live: dynamically imported the module in the running
dev page and confirmed the graph — two `DynamicsCompressorNode`s created,
the 3.2 makeup gain scheduled, all four cues (`navigate`/`select`/`toast`/
`intro`) fire and `intro`'s `stop()` runs without throwing.

## Rules for anyone extending this

- A cue is a few lines of oscillator/gain-envelope math (see `blip()`).
  Keep new cues short (well under 200ms) and modest in raw `gain`
  (roughly 0.1-0.16 for a repeated UI tick, not the intro's ~0.5) — this
  is UI feedback, not a soundtrack. The `gain` value is no longer the
  only lever, though: every voice now passes through the
  `getMasterInput()` compressor/makeup/limiter chain before reaching
  destination, so raw `gain` mainly sets that chain's *input* balance
  between simultaneous voices — final loudness is shaped by the chain,
  not by `gain` alone. Don't try to get louder by raising `gain` toward
  1.0; if a cue still isn't loud enough, the makeup gain in
  `getMasterInput()` is the one shared knob to revisit. **`intro`
  remains the one documented exception** to the "modest gain" guidance
  above — a one-time signature moment (not a repeated UI tick) is
  allowed a longer duration and higher per-voice gain. Don't use that as
  precedent for a new repeated cue; it's specific to something that
  plays once per session.
- **If a cue plays multiple voices simultaneously** (like `intro`'s
  three-layer chord), budget their gains so the peaks sum to well under
  1.0, not just under-1.0 each independently. Web Audio sums overlapping
  voices at the destination with no automatic normalization — cranking
  each voice's gain up in isolation, without checking what plays at the
  same time, clips (harsh digital distortion) instead of sounding
  louder. `intro`'s three overlapping voices are tuned to sum to ~0.95
  at their shared peak.
- Every consumer should go through `useSound()`, not call `sounds.*`
  directly, so the Settings gate is never accidentally bypassed. The one
  documented exception above is deliberate; don't add a second one
  without an equally specific reason.
- If this folder grows a second concern unrelated to audio, give it its
  own file rather than overloading `sound.js` — the folder is for
  non-visual utilities generally, not exclusively audio, but each file
  should still own one concern.
