# src/lib/ — non-visual utilities

Parent: [`../CLAUDE.md`](../CLAUDE.md) → [`/CLAUDE.md`](../../CLAUDE.md).
Any change in this folder updates this file and the root repo map in the
same change.

**New folder this batch.** Everything else under `src/` fit one of the
existing categories (`components/` = presentational + interaction
plumbing, `context/` = React state, `data/` = content, `screens/` =
routes, `styles/` = CSS, `assets/` = static files) — a sound *engine* is
none of those. It has no JSX, isn't a React Context, and doesn't own any
component-shaped state, so it lives here instead of being awkwardly
homed in `components/`.

## Files

| File | Status | Notes |
|---|---|---|
| `sound.js` | ✅ | Synthesizes short UI sound cues with the Web Audio API — no audio files, so zero bytes added to the JS bundle. Exports `sounds` (`navigate`, `select`, `toast`, `intro` — each a plain function, no React), `useSound()` (a hook that reads `useSettings().sound` and returns a `playSound(name)` callback that no-ops when the toggle is off), and `hasHadUserGesture()` (see below). Built after an earlier pass shipped a "Sound" toggle in OPTIONS with nothing behind it (removed, then reinstated once this existed) — see `../components/CLAUDE.md`'s `MainMenu.jsx` and `ToastProvider.jsx` entries for where each cue is wired in. **Why Web Audio instead of files:** creating/resuming an `AudioContext` requires a prior user gesture in every modern browser, so this cannot autoplay by construction — spec §2's "never autoplay" rule is enforced by the platform, not by discipline that could later lapse. `sounds.select()` is called directly (bypassing the `useSound()` gate) in exactly one place — the SOUND toggle button itself in `MainMenu.jsx` — so turning sound on gets an immediate audible answer instead of silence until the next unrelated click. **`toast` retuned this batch:** the user asked for the memory-toast cue to feel less energetic and darker than the bright `freq: 640 → glideTo: 860` chime it shipped with. It's now `freq: 260 → glideTo: 170` — lower starting pitch, glides *down* instead of up, held a touch longer (0.22s vs 0.15s) — so it reads as a quiet acknowledgment rather than a mini fanfare, distinct in character (not just volume) from `navigate`/`select`, which both stay bright since they're momentary interaction feedback rather than a mood beat. Verified live: patched `AudioContext.createOscillator` to log the actual frequency values fired on a real `episodeFirstOpen` toast. **New this batch — `intro`:** the site's one-time "signature sting" on first landing on the main menu, the user's "alike how Netflix has its signature tune" request. `blip()` gained an optional `delay` param (seconds from now) so a handful of calls can be chained into a short motif instead of needing a real sequencer — `intro` schedules three notes (C3 → Eb3 → G3 at 0/150/320ms, `triangle`/`sine`) with the held final note gliding *down* to F3 rather than resolving up, deliberately dark/moody rather than a bright fanfare, matching the same "something darker" direction the `toast` retune took. ~0.9s total. Fired from `src/screens/TitleScreen.jsx`, gated by the same `hasPlayedIntro` module flag that already skips beats 1–2 on a same-session return to `/` — see that file. Like every other cue it's silent unless the Settings sound toggle is on, and can't autoplay before a user gesture regardless (standard `AudioContext` autoplay policy, already true of every cue here — nothing new added for this one). Verified by dynamically importing the module in the running page and capturing the actual scheduled frequencies/delays via a patched `createOscillator`. **Retuned louder immediately after, on direct feedback** ("that sound is a bit TOO small... make it louder and proper"): gains roughly 2.5x (e.g. the C3/Eb3 notes went `0.05`/`0.055` → `0.13`/`0.14`), well past the "well under 0.1" guidance below — deliberately, since `intro` is a one-time signature moment, not a repeated UI tick, and is the one cue allowed to be an exception to that rule. The single closing G3→F3 tone also became a real three-layer chord hit (a C2 sub-bass for weight underneath, the G3→F3 glide carrying the melody, and a quiet octave-up G4→F4 shimmer on top) rather than just turning one oscillator's gain up — layering is what reads as "proper" fullness rather than a loud thin blip. **Retimed and made interruptible this batch**, per two more live notes: "the sound doesn't play on reload" (see below — expected autoplay-policy behavior, not a bug, now documented rather than silently mysterious) and "it should play the moment the second loading screen comes and stop when the menu loads." `intro` now starts on beat 2 (`TitleReveal`) instead of beat 3, matching where Netflix's own sting actually plays (during the brand animation, not after the home screen has already loaded). Making it stoppable needed real plumbing: `blip()` now returns its `{ osc, amp }` node pair instead of nothing, a new `fadeOutVoices()` helper cancels each voice's scheduled envelope and ramps it to silence over ~50ms, and `sounds.intro()` collects its five voices and returns a `stop()` closure over `fadeOutVoices(voices)` — the first cue in this file whose return value matters, so `useSound()` was changed to pass a cue's return value through instead of discarding it. `TitleScreen.jsx` calls the returned `stop` from its beat-2 effect's cleanup, so the tune is cut off the instant the beat actually moves on to MENU (via `TitleReveal`'s own hold timing out OR the visitor skipping it early), rather than only ever being allowed to finish on its own. **On "doesn't play on reload":** verified this is the browser's autoplay policy working as intended, not a defect — beats 1–2 auto-advance on their own timers with zero interaction required (spec's "no forced interaction" rule), so a visitor who never clicks/taps/presses a key during them never produces a user gesture on that pageload, and no `AudioContext` can play audio without one. `getContext()`'s `ctx.resume()` call now also `.catch()`s its rejection in that case, so it fails silently instead of logging an unhandled-rejection warning for expected behavior. Skipping a beat (already supported) supplies the gesture and unlocks audio for the rest of the session. Verified live: patched `createOscillator`/`createGain` to confirm `sounds.intro()` returns a real function and that calling it fires `cancelScheduledValues` + a ramp-to-`0` + an `osc.stop` scheduled ~60ms out for all five voices. **Retuned louder a second time immediately after** — the first "louder" pass wasn't enough ("EXTREMELY LOW... can't hear it at 100 percent volume without headphones" on real speakers). This pass is roughly another 3x on top of that, not an incremental nudge: C3/Eb3 `0.13`/`0.14` → `0.44`/`0.46`, and the three-voice chord layer (sub-bass/root/shimmer) `0.11`/`0.18`/`0.07` → `0.3`/`0.5`/`0.15`. The chord gains specifically were budgeted, not just multiplied independently — those three voices play simultaneously and Web Audio sums overlapping voices at the destination with no automatic normalization, so pushing each one to a "loud" value in isolation would clip (harsh distortion) rather than sound louder; they're tuned so their peaks sum to ~0.95, just under the 1.0 clipping ceiling. Verified live: captured the actual scheduled gain peaks (`0.44, 0.46, 0.3, 0.5, 0.15`) and computed the three-voice chord's simultaneous sum (`0.95`) via a patched `createGain`. **Fixed a real bug this batch, not just an autoplay-policy explanation:** "I still can't hear shit until I CLICK" turned out to be caused by the intro effect burning its one-shot flag on a guaranteed-silent attempt. The old `TitleScreen.jsx` effect called `playSound('intro')` and set `hasPlayedIntro = true` unconditionally the instant beat 2 was reached — including when that happened via `TitleReveal`'s own timer, with zero gesture yet. The AudioContext correctly refused to resume (no gesture = no audio, exactly as documented above), but the flag had already flipped, so a *later* click could never trigger the cue again — it had already been marked "played." New export **`hasHadUserGesture()`** wraps the standard User Activation API (`navigator.userActivation.hasBeenActive`) to answer, synchronously and without guessing, whether this pageload has had a real click/tap/key yet; returns `null` (not `false`) on browsers that don't support it (older Safari/Firefox) so callers can fall back rather than get a wrong answer. `TitleScreen.jsx` now checks this before playing `intro`: if a gesture already happened, it plays immediately as before; if not, it attaches a one-time `pointerdown`/`keydown` listener (scoped to while beat 2 is showing) and plays on the first real one instead of right away — so a click during the intro now genuinely unlocks the sting rather than arriving after it already silently failed. Verified live that `navigator.userActivation.hasBeenActive` correctly reads `false` on a fresh untouched load, confirming the detection path; full click-triggers-playback verification needs a real browser session with actual trusted input — the sandboxed browser tool used for other verifications in this repo can't dispatch a trusted gesture (clicks don't register at all in its current headless state), so that specific path is traced by code review rather than a live capture. **Lengthened this batch** on direct feedback that the sting felt too short: the held closing chord's duration and delay grew (C2 sub-bass/G3→F3 `0.6s`→`1.1s`, G4→F4 shimmer `0.55s`→`1.0s`, delays `0.32`/`0.33`→`0.38`/`0.39`; the opening two notes also nudged `0.18s`→`0.22s` with a slightly wider gap). Note count and gains are unchanged — only sustain, ~0.9s → ~1.5s total — so it's still comfortably inside `TitleReveal.jsx`'s 1.8s hold and finishes naturally when that beat isn't skipped early. |

## Rules for anyone extending this

- A cue is a few lines of oscillator/gain-envelope math (see `blip()`).
  Keep new cues short (well under 200ms) and quiet (gain well under
  0.1) — this is UI feedback, not a soundtrack. **`intro` is the one
  documented exception** — a one-time signature moment (not a repeated
  UI tick) is allowed a longer duration and gain up to ~0.5. Don't use
  that as precedent for a new repeated cue; it's specific to something
  that plays once per session.
- **If a cue plays multiple voices simultaneously** (like `intro`'s
  three-layer chord), budget their gains so the peaks sum to well under
  1.0, not just under-1.0 each independently. Web Audio sums overlapping
  voices at the destination with no automatic normalization — cranking
  each voice's gain up in isolation, without checking what plays at the
  same time, clips (harsh digital distortion) instead of sounding
  louder. `intro`'s three overlapping voices are tuned to sum to ~0.95
  at their shared peak.
- Every consumer should go through `useSound()`, not call `sounds.*`
  directly, so the Settings gate is never accidentally bypassed. The one
  documented exception above is deliberate; don't add a second one
  without an equally specific reason.
- If this folder grows a second concern unrelated to audio, give it its
  own file rather than overloading `sound.js` — the folder is for
  non-visual utilities generally, not exclusively audio, but each file
  should still own one concern.
