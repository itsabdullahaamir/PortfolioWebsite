# src/context/ — global state

Parent: [`../CLAUDE.md`](../CLAUDE.md) → [`/CLAUDE.md`](../../CLAUDE.md).
Any change in this folder updates this file and the root repo map in the
same change.

`ProgressContext.jsx` and `SettingsContext.jsx` are done and match spec
§7 ("React Context for progress + settings. Persist to localStorage. No
state library needed."), both mounted in `App.jsx`. `MusicContext.jsx`
(new this batch) is a third, small, unpersisted context — see its row
below and `../CLAUDE.md`'s App.jsx note for why it exists.

| `MusicContext.jsx` | ✅ | `useMusic()` exposes `{ started, start, trackIndex, next, previous, hasPrevious, hasMultipleTracks }`. `started`/`start` are a one-way session flag (no persistence, no `stop()`) tracking whether `BackgroundMusic.jsx` has ever been unpaused-for-real this session. Exists because `BackgroundMusic.jsx` moved from being mounted by `MainMenu.jsx` (start-on-mount, stop-on-unmount) to being mounted once in `App.jsx`, outside the routed screens, so it can survive route changes — direct user request that the radio keep playing across navigation rather than stopping every time the visitor left the menu. (That request has since widened twice: first to `/` + `/plain` only, with `/chapters` and `/chapters/:id` still pausing; now to every route, the pause gate removed entirely — see `../components/CLAUDE.md`'s `BackgroundMusic.jsx` row. `started` is unaffected by that change and remains the only gate this context owns.) `TitleScreen.jsx` calls `start()` the instant its beat sequence reaches MENU, which is what keeps the radio from starting during beats 0–2 (StartPrompt/PresentsCard/TitleReveal) even though `BackgroundMusic.jsx` itself is now mounted from page load. **This batch — track selection moved here too**, out of `BackgroundMusic.jsx`'s local state, on direct user request for Previous/Next Track controls in `MainMenu.jsx`'s OPTIONS panel: those controls need to change the same track the radio is playing without reaching into the component that owns the `<audio>` element, so the shared bit of state (which track index is current) now lives in this context instead. It's a `{history, pointer}` pair, not a bare index — `next()` either replays forward through existing history (a "redo," if `previous()` was called earlier) or rolls a new random track (excluding the current one) and appends it; `previous()` steps the pointer back, a no-op at the start of history (`hasPrevious` reflects this so the OPTIONS button can disable itself). This preserves `BackgroundMusic.jsx`'s existing "shuffled, not sequential" design — see that file's row — while making "go back" actually mean something instead of jumping to another random track. See `../components/CLAUDE.md`'s `BackgroundMusic.jsx` row for the pause/resume mechanism (route-based, inside that component, not this context) and its `MainMenu.jsx` row for the new OPTIONS controls. **This batch — the shuffle itself was fixed**, on a direct live report ("when I go next track, sometimes the same track comes back after 2-3 tracks. This means it's not optimized very well"). `next()` used to roll `Math.random()` and exclude only the track currently playing. That is memoryless: at 14 tracks the chance of *some* repeat inside any four-track window is already over 20%, so what was reported is correct behavior for that algorithm rather than a stray bug — which is why the fix is a different algorithm and not a tighter exclusion. Selection is now a **shuffled bag**. `shuffledIndices()` (Fisher-Yates) produces a permutation of every playlist index; `next()` consumes it from the front, one track per call; only when it empties does `refillBag()` build another. That alone buys the guarantee the die roll could not — every track plays once before any plays twice — but it leaves a seam, because a track sitting at the END of one bag can reappear near the START of the next, two or three skips later, which is precisely the reported symptom rather than a milder version of it. So `refillBag(recent)` takes the tail of what just played and builds the new bag position by position, choosing the first track in a pre-shuffled pool that is not inside the no-repeat window `GAP` (half the playlist — 7 of 14 today), falling back to the pool's next entry when nothing legal remains so that it always terminates, unlike rejection-sampling a whole permutation. `GAP` is half and deliberately **not** `length - 1`: forbidding every recent track fully determines the next bag's order and degenerates shuffle into a fixed rotation. The bag lives in the same state object as `history`/`pointer`, not in a ref, because mutating a ref inside a state updater would be re-run — and so double-consume the bag — under StrictMode's intentional double-invocation. Verified by extracting the real helpers out of this file and driving them directly: across 150,000 simulated plays at the live 14-track length the smallest gap between two plays of the same track is **8** (never under the 7 the window promises, against **2** for the old picker), zero back-to-back repeats, per-track share 7.13–7.16% against an even 7.14% — so the fix costs nothing in uniformity — Previous-then-Next replays the identical history rather than re-rolling, and 1-, 2- and 3-track playlists all behave sanely. |

## Rules for anyone extending these

- Both hooks throw if used outside their provider — keep that pattern for
  any new context added here rather than silently returning defaults.
- `localStorage` keys (`tt_resume_progress`, `tt_resume_settings`) are
  part of the spec's naming (§5 mechanic 3 names the progress key
  explicitly) — do not rename without updating both this file and the
  root `CLAUDE.md`.
- If a further context becomes necessary, add it here and update this
  table plus the root repo map — do not bolt extra state onto existing
  providers. (`MusicContext.jsx`, above, is the precedent for when this
  was worth doing: a genuinely separate concern from progress/settings,
  not a settings toggle, which stays in `SettingsContext.jsx`.)
